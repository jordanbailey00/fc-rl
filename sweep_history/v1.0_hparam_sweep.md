## Executive Summary

- All 96 trials finished the configured budget. Every local log contains the
  same 145 metrics at five snapshots, for 69,600 finite stored metric values.
  There were no missing metrics, NaNs, infinities, OOMs, or failed trials.
- The primary in-sweep baseline, `gp2dfafs`, reached cave progress `0.763622`
  and average wave `48.703`. It never reached wave 63 in its final evaluation.
- `cx70p9ch` is an exact deterministic duplicate of `gp2dfafs`. PufferLib ran
  the default center twice before beginning adaptive suggestions.
- The best observed run was `ge0h4chm`: cave progress `0.937295`, average wave
  `59.643`, wave-63 reach rate `69.896%`, and cave completion rate `5.750%`.
  It completed 581 of 10,105 evaluated caves and did not exhibit the healing
  loop.
- The raw second-place run, `fi6th21p`, is not a clean recommendation. It
  combined strong progress with a serious Yt-MejKot healing loop: `47.854%`
  healing-to-gross-damage, `63.266%` Yt-MejKot target share, and an average
  longest wave of 12,532 ticks.
- The two strongest clean runs, `ge0h4chm` and `luiq0j2s`, landed in a narrow
  common parameter region. Several weaker but still useful runs used very
  different settings, so the sweep identifies a leading basin rather than one
  proven exact optimum.
- All trials used trainer seed 73. Final evaluation covered many episodes, but
  that does not measure training-seed variance. The leading configurations
  still require independent-seed confirmation.
- The healing loop appeared severely in 19 of 96 runs. Another 16 runs had
  mixed or suspicious healing between 10% and 50% of gross damage. Healing
  alone is not sufficient to declare an exploit, so episode duration,
  Yt-MejKot targeting, and longest-wave duration were considered together.
- The smallest targeted correction is to activate the already implemented
  `shape_npc_heal_penalty` at `-0.01`. This is a one-key reward configuration
  change. It fires only when an NPC actually restores HP and leaves backend,
  observations, actions, progression rewards, and prayer mechanics unchanged.

regimes.

The alternate regions did not match `ge0h4chm` on cave progress, Jad reach, or
completion. They are evidence against claiming one exact mathematical optimum,
but they are not stronger practical choices than the leading basin.

## Healing Loop Root Cause

The healing loop, correct-prayer farming, and avoidance of stall penalties are
different parts of one learned behavior:

1. The policy attacks a Yt-MejKot and receives positive net-progress reward
   for the damage dealt.
2. The Yt-MejKot heals itself or another NPC. That restoration produces
   negative net progress, so damage and healing approximately cancel over a
   repeated cycle.
3. Every new damaging hit is still considered positive progress for that tick
   and resets `ticks_since_positive_progress` to zero.
4. Repeated attack attempts reset `ticks_since_attack` to zero.
5. The Yt-MejKot continues making melee attacks. Correct protection against an
   eligible non-Jad hit pays a repeatable positive reward.
6. The agent therefore remains active enough to avoid the inactivity channels
   while collecting a renewable prayer reward from a fight it does not finish.

### Exact reward economics

| Channel | Value | Effect in the loop |
|---|---:|---|
| `w_correct_danger_prayer` | `+0.005` per eligible correct non-Jad styled hit | Renewable positive reward from correct melee protection |
| `w_tick_penalty` | `-0.0001` per tick | One correct prayer pays for 50 ticks of base time penalty |
| `w_progress` | `+0.001` per net required-work unit removed | Damage pays positively and healing pays negatively; repeated cycles approximately cancel |
| `shape_npc_heal_penalty` | `0.0` | No additional cost when an NPC successfully restores HP |
| `shape_no_attack_base_penalty` | `-0.005`, after 50 eligible ticks | Avoided because the policy keeps issuing attacks |
| `shape_no_attack_wave_scale` | `0.05` per wave after wave 1 | Does not help when attack attempts keep resetting the timer |
| `shape_no_progress_penalty_1` | `-0.001` after 800 ticks | Usually avoided because each damaging hit resets the timer |
| `shape_no_progress_penalty_2` | Additional `-0.005` after 1,600 ticks | Same timer-reset weakness |
| `shape_no_progress_penalty_3` | Additional `-0.02` after 2,400 ticks | Same timer-reset weakness |
| Wave-stall penalty | Disabled at `0.0` | No direct cost based only on total time in the wave |

The progress reward itself is not repeatedly creating free net progress. Its
positive and negative sides approximately cancel when damage is healed. The
problem is that positive damage resets the no-progress timer even when the
work is later restored, while the independent correct-prayer reward remains
positive.

### Concrete exploit example: `5bwnu6a1`

| Metric | Value |
|---|---:|
| Average wave | 28.65 |
| Healing / gross damage | 96.47% |
| Yt-MejKot target share | 97.87% |
| Average episode length | 103,489 ticks |
| Progress reward accumulated before/during loop | +28.195 |
| Correct-danger-prayer reward | +99.820 |
| Tick penalty | -10.341 |

This policy earned a larger episode return than clean winner `ge0h4chm`
(`103.836`) while reaching only about half as far through the cave. PufferLib's
sweep objective was external cave progress, so Protein did not rank this policy
highly. PPO inside the run still optimized the exploitable scalar reward and
could settle into the loop.

## Minimal Healing-Loop Corrections

No correction below has been applied by this document.

### Option A: activate the existing actual-heal penalty

Recommended first experiment:

```ini
shape_npc_heal_penalty = -0.01
```

Why this is the smallest targeted change:

- It is one configuration value. No backend, observation, action, policy, or
  PufferLib code changes are needed.
- The existing reward channel fires once only when an NPC heal actually
  restores HP. A failed heal or an NPC that never heals produces no penalty.
- It targets the event that distinguishes the pathological loop from normal
  combat. It does not punish standing in a particular location, safespotting,
  movement, target switching, prayer flicking, or ordinary attack cadence.
- It also discourages successful Yt-HurKot healing on Jad, which is aligned
  with cave completion rather than an unrelated behavior.

Why `-0.01` is the recommended initial value:

- Yt-MejKot restores at most 100 internal HP units per successful proc.
- `5bwnu6a1` recorded 903,429 restored units, proving at least 9,035 successful
  heal procs. Partial heals would make the actual proc count higher.
- At `-0.01` per proc, unchanged exploit behavior would receive at least
  `-90.35` additional reward per episode.
- Its current correct-prayer reward is `+99.82`; its tick, no-attack, and
  no-progress penalties already total about `-12.95`. Adding at least `-90.35`
  makes the observed loop decisively unprofitable.
- Clean winner `ge0h4chm` recorded only 4,136 restored units, or at least 42
  procs. The same coefficient would add roughly `-0.42` at the lower-bound proc
  count, small relative to its `+106.56` progress reward.

This is intentionally stronger than `-0.005`. At the empirical lower-bound
proc count, `-0.005` would charge only about `-45.18` in `5bwnu6a1`, leaving a
large amount of the repeatable prayer income intact.

The first validation should change only this key and hold the selected
hyperparameters, trainer seed, backend, observations, loadout, and 750M budget
fixed. Primary acceptance checks are:

- Healing remains below approximately 5% to 10% of gross damage.
- No return of multi-thousand-tick Yt-MejKot waves.
- Cave progress and wave-63 reach remain near the clean winner's range.
- Correct-prayer accuracy does not materially regress.
- Progress reward, rather than correct-prayer reward, remains the dominant
  positive return channel.

### Option B: reduce the globally repeatable prayer reward

Fallback configuration-only experiment:

```ini
w_correct_danger_prayer = 0.002
```

At `0.002`, the `5bwnu6a1` prayer channel would fall from about `+99.82` to
about `+39.93` if behavior remained unchanged. This also makes one correct
prayer pay for 20 base-penalty ticks instead of 50.

This is broader than Option A. It changes the learning signal for every
non-Jad danger prayer, including legitimate early learning and clean late-wave
combat. It should be tested only if the direct heal penalty does not remove the
loop or if policies find another renewable correct-prayer farm.

### Option C: reset no-progress only on a new progress high-water mark

Instead of resetting the no-progress timer on every damaging hit, reset it
only when required work falls below the best value previously achieved in the
current wave. Re-damaging HP that was just healed would no longer reset the
timer.

This directly closes the timer bypass, but it requires reward-runtime code and
state changes. It also changes behavior in every wave containing healing, so it
has a larger regression surface than enabling the existing heal penalty.

### Option D: restore a small wave-duration penalty

A small penalty after an unusually long wave would eventually make any loop
unprofitable. This is simple in configuration but broad in behavior: it also
penalizes legitimate slow late-wave fights, pathing recovery, and defensive
play. It is not recommended before the event-specific heal penalty.

### Recommended order

1. Test only `shape_npc_heal_penalty = -0.01`.
2. Preserve `w_correct_danger_prayer = 0.005` during that test so prayer
   learning is not disturbed and attribution remains clean.
3. If healing loops remain, test `w_correct_danger_prayer = 0.002` separately.
4. Consider the progress high-water-mark timer only if configuration-only
   changes fail.
5. Avoid combining fixes in the first run. A one-variable test is necessary to
   know which correction changed behavior.

Episode truncation, backend healing changes, removal of prayer observations,
and reintroduction of damage-dealt reward are not recommended for this issue.
They affect substantially more behavior than the demonstrated reward gap.

## Final Conclusions

1. `ge0h4chm` is the clear best observed run and clean practical candidate.
2. `luiq0j2s` confirms the same high-performing hyperparameter basin.
3. `5mpum7x7` demonstrates a separate viable basin but does not match the
   winner's final progress or Jad conversion.
4. Raw cave-progress ranking is insufficient on its own. `fi6th21p` ranks
   second while containing a major healing loop, and `vxpabmtb` ranks seventh
   with pathological stalls.
5. The exact optimal hyperparameters are not established because all trials
   used one trainer seed and Protein sampled adaptively.
6. The healing loop is a reward-alignment problem, not evidence that NPC
   healing mechanics are malfunctioning.
7. The most focused first correction is the existing per-actual-heal reward
   channel at `shape_npc_heal_penalty = -0.01`, tested as the only change.
